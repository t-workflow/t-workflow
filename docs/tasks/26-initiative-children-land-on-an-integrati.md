# 26 — Initiative children land on an integration branch; the human gate is the initiative's PR to the trunk
Issue: #26

## Asked
An initiative's children no longer reach the trunk one PR at a time. A child's PR on its own may not be self-consistent, so nothing of an initiative lands on the trunk until the whole initiative does. Every child of a parent issue labelled `initiative` branches from, and opens its PR against, one integration branch `wip/<parent-id>-integration`, created from the trunk by the first child's `/t-work` when absent, whether the child is worked by hand or under `/t-drive`. A child merges into the integration branch on a mechanical gate alone — CI green, and a current ready cold review when its diff is protected — and no human is asked, driven or by hand; its issue is closed as completed at that merge, because GitHub's `Closes` keyword only fires on the default branch and the next child's blocker gate reads "closed as completed". The human's single gate is the initiative's own PR from the integration branch to the trunk, shipped through `/t-ship <parent-id>` with the usual confirmation question. That PR is a parent's PR: its records are the children's records already on the branch, its plans are the children's plans, its cold review reads the combined diff when any of it is protected, and its squash commit carries one `Task:` line per child. The ship gate for a parent refuses while any child is still open: a child that fails its bounded retry under `/t-drive` stops the drive with a report instead of being skipped, and only fixing it or cancelling it (an explicit statement that the initiative is consistent without it) unblocks the ship. Cancelling a child already merged into the integration branch reverts it there. The integration branch gets the same GitHub protection the trunk has, applied by the installer as a pattern rule on `wip/*-integration` (PRs only, the `t-workflow` check required, deletions allowed so the branch can go once the parent merges). Long-lived drift from the trunk is accepted; conflicts are resolved on the integration branch as a fix pass before the final PR. Every tracker read stays keyed by issue number; the parent relation is read from the issue, never from a label on the child.

## Done when
- `gate.sh work <child>` prints `base: wip/<parent>-integration` for a child of an initiative, creating the branch from `origin/<trunk>` when it does not exist, and `/t-work` branches from and rebases onto that base; a plain task still reports the trunk.
- `gate.sh ship <child>` accepts a PR whose base is the integration branch and reports `merge: automatic`; `/t-ship` on it marks ready, watches CI, squash-merges on green without a question, and closes the issue as completed.
- `gate.sh ship <parent>` accepts the integration PR to the trunk: blocks while any child is open, while any child's record is missing from the diff, while a protected combined diff has no current ready cold review; requires no `## Plan` on the parent.
- `ci.sh` on a child PR (base = integration branch) applies the same rules as today; on the parent's PR it checks every child's record and the combined review instead of a parent record and plan.
- `/t-drive <parent>` runs every child to its integration merge without asking, stops with a report on a child that fails its retry, and ends at the parent's `/t-ship` confirmation.
- `/t-cancel` on a child merged into the integration branch reverts that child there before closing.
- `protect.sh` applies a pattern rule for `wip/*-integration` requiring the `t-workflow` check, PRs only, deletions allowed, merging into an existing rule rather than replacing it, with the same paid-plan and read-failure handling the trunk's rule has; `install.sh` runs it in the same modes.
- `tests/test.sh` covers the new gate outputs against fixtures and passes.
- `.t-workflow/AGENTS.md`'s CI paragraph says that enforcement is read from a PR's base branch, so a child PR is judged by the integration branch's copy of the scripts and policy, while the initiative's PR to the trunk is judged by the trunk's copy on the combined diff; the guarantee that a PR cannot rewrite its own enforcement holds at the trunk, and the gate before a child merge is mechanical only.
- The plan and the trace start from the trunk as it is after #13 (PR #22), which rewrote parts of `ci.sh`, `lib.sh`, `tests/test.sh`, and the contract's CI paragraph.
- `docs/decisions.md` has one entry replacing the 2026-09-08 "No initiative integration branches" decision, with the reason.
- Trace in the record: one initiative with children A and B, B blocked by A, through every event — A's push, review, CI, merge, close; B's gate; the parent's PR, review, CI, confirmation, merge — naming what turns each red state green without a human.

## Explicitly not
- The trunk's protection is unchanged.
- Migrating in-flight initiatives: a child PR already open against the trunk when a consumer updates is retargeted by hand or shipped first.
- A per-child human question in any form.
- Shipping an initiative with a child excluded.

## Decisions made along the way
- A child is any issue whose own `parent` field is set; the parent's label is not read again. `t-open` labels every parent `initiative`, so the two agree, and it saves a tracker read per gate.
- `gate.sh work <child>` creates `wip/<parent>-integration` on origin from `origin/<trunk>` when absent, as the issue says; it is the one write the gate makes.
- A child's ship gate prints `merge: automatic`; `/t-ship` then skips the confirmation and closes the issue itself, because `Closes` only fires on the default branch. A task's and a parent's gate print `merge: confirm`.
- The parent's PR is opened by `/t-ship <parent>` when the gate reports none: the gate prints the exact `gh pr create` so the skill runs it and gates again. Nothing opens it earlier, because a cold review needs a PR and the review comes after the last child.
- The parent's ship gate and `ci.sh` read the children with their `stateReason`: an open child blocks, a completed child's record must be in the diff and valid, a cancelled child's record must not be (its revert has to have landed). No `## Plan` is asked of the parent; each child was gated on its own.
- The integration branch is PR-only, so a conflict with the trunk is resolved through a child task that merges `origin/<trunk>` into its branch; the parent's gate names that.
- A cancelled child already on the integration branch is reverted through a PR on the mechanical gate (`wip/<id>-revert`); the revert takes the record with it, and `ci.sh` accepts a deleted record only for an issue closed as not planned, which is what makes the parent's gate (no cancelled child's record in the diff) reachable. A protected revert names `/t-review <id>` first. The alternative, an admin pushing the revert, would bypass the rule the branch exists for.
- `ci.sh` tells a parent's PR by the issue's `initiative` label, as `gate.sh` does, never by the branch name, so a task whose title slugifies to `integration` is still a task.
- The pattern rule goes through GraphQL (`createBranchProtectionRule` / `updateBranchProtectionRule`): the REST branch-protection endpoint takes an exact branch name. Only the required-checks list is merged into an existing rule; a free private plan is reported and exit 0, an unreadable rule list stops before any write. `install.sh` needed no change: protect.sh applies both rules in one run, in the same modes as before.
- `snapshot.sh review <parent>` carries `children[].plan` and `children[].record`, and `/t-review` reads those as the parent's; `snapshot.sh status` shows a parent's integration branch and PR.

## Deviations / notes
- `.claude/skills/t-review/SKILL.md` is touched though the issue's Scope did not list it; the plan added it, because the reviewer would otherwise fail the parent's PR for having no plan.
- The plan's first risk — whether GitHub lets a branch be created when it matches a rule with required status checks — could not be verified: the probe (a throwaway rule and branch on this repository) was refused by the session's permission layer, and nothing else here can answer it. The first initiative driven after this merges answers it; if creation is refused, the fallback named in the plan is the same rule applied by exact name after the branch exists.
- Ride-along fix in `gate.sh`: in the ship stage, `rc=$?` after `if ! pr=$(pr_for_task ...)` read the negated status, so the "no PR for #<id>" and "already merged" lines were never printed (the gate exited 1 with no `BLOCKED:` line). Caught by the new test for a parent with no PR; fixed by capturing the status before the `if`.
- The "close the parent?" question at the end of a child's `/t-ship` is gone: the parent closes when its own PR merges into the trunk (`Closes #<parent>` in its body).
- Fix pass after the cold review (not-ready, three High): (1) `snapshot.sh review <parent>` crashed on a literal backslash in its jq program — fixed and covered by a test; (2) `protect.sh` sent the pattern rule's required checks to GraphQL as one string, which GitHub coerced into a single bogus check — now one `-F 'ctx[]=…'` per context, the test asserts the typed form; (3) the cancel path was unreachable: the skill restored the record the parent's gate requires gone, and a plain revert failed the revert PR's own CI — now the revert removes the record and `ci.sh` accepts that for a cancelled issue, covered by tests. Also from the review: the work gate now prints git's refusal text when the integration branch cannot be created; parenthood in `ci.sh` comes from the label; tests cover `snapshot.sh review` and `status` for a parent; the PR's checks list names the ship gate run.

## Trace
One initiative P with children A and B, B blocked by A. Each red state and what turns it green with no human in the loop:

1. `/t-drive P` → `gate.sh work A`: P's integration branch `wip/P-integration` is absent → created on origin from `origin/main`; `base: wip/P-integration`. `/t-work A` branches from it, opens a draft PR against it. CI does not run on a draft.
2. A's diff is protected → `/t-review A` in a subagent posts `readiness: ready`; `rerun-ci.sh` finds no run (still a draft), says so.
3. `/t-ship A` → `gate.sh ship A`: base is the integration branch, `merge: automatic`, record and review current. `gh pr ready` → CI starts from the integration branch's copy of the scripts (`pull_request_target`, base = integration branch): record, title, plan, review present → green. Squash-merged with no question; `gh issue close A --reason completed`. The `Closes` keyword did not fire (not the default branch), which is why the skill closes it.
4. `gate.sh work B`: blocker A is closed as completed → passes; `base: wip/P-integration` (exists, reused). B branches from it, so it sees A's change. Same path as A to its merge and close.
5. No child open → `/t-ship P` → `gate.sh ship P`: no PR → the gate names `gh pr create --draft --base main --head wip/P-integration --title "[P] …"`; the skill runs it and gates again. Every child closed as completed, both records in the diff and valid, the combined diff is protected → `BLOCKED: protected diff with no cold review`.
6. `/t-review P` in a subagent reads the children's plans and records from the snapshot, reviews the combined diff, posts `ready`; `rerun-ci.sh` — the PR is a draft, nothing to re-run.
7. `/t-ship P`: gate passes, `merge: confirm`. `gh pr ready` → CI from the trunk's copy: children's records, title, review current, blockers → green. The confirmation question is the run's stop. On `merge`: squash with one `Task:` line per child, `Closes #P` closes P, `delete_branch_on_merge` deletes the integration branch (the pattern rule allows deletion).
8. Red states without a human: a child's CI red because its review is missing → `/t-review` + `rerun-ci.sh`; a child `not-ready` → one `/t-work` fix pass and one re-review, then the drive stops with a report and P's gate blocks on the open child; a cancelled child → `/t-cancel` reverts it on the integration branch through a PR whose CI accepts the record's deletion because the issue is closed as not planned, and P's gate stops blocking once that record is out of the diff; a conflict between the integration branch and the trunk → P's gate names a child task that merges the trunk in.
