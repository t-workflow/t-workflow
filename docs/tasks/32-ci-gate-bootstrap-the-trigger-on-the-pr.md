# 32 — CI gate: bootstrap the trigger on the PR that introduces it
Issue: #32

## Asked
Since #13 the CI gate triggers on `pull_request_target` only, so GitHub reads `.github/workflows/t-workflow.yml` from the base branch and a PR cannot edit the gate that judges it. The PR that introduces or changes that trigger gets no `t-workflow` run at all: the base's copy does not listen for `pull_request_target`, and the PR's copy is not consulted for it. The required check then never reports and the PR can only merge by admin bypass. This happened on #22 itself (its head commit has shellcheck and test runs only), and it hits every consumer twice: a fresh adoption, whose base has no workflow file, and every `/t-update` from v0.0.5, whose base has the old `pull_request` copy. The installer has already made the check required in both cases, so both are a hand step at install or update time.

Fix it by adding `pull_request` back as a second trigger on the same job, restricted with a `paths` filter to PRs that touch `.github/workflows/t-workflow.yml`. Those are exactly the PRs whose base copy is missing or listens for the wrong event, so the PR's own copy runs there and nowhere else: an ordinary PR at steady state gets no `pull_request` run, not even a skipped one, and the base's `pull_request_target` run remains the only check. A PR that edits the workflow at steady state gets two runs under one name; both fetch the gate scripts from the base and judge the same PR. It was verified live on 2026-09-11 (a throwaway repo, one job named `t-workflow` under both triggers, the check required, admin enforcement on, four PRs covering every order of red and green) that GitHub blocks the merge when any run under the required name failed, whichever finished last, and `gh pr merge` refuses with "the base branch policy prohibits the merge". So a PR's own run can add a red result but never override one; the guarantee from #13 holds unchanged.

Under `pull_request` the default checkout is the PR's merge commit, not the base. The job already fetches the gate scripts from the base by ref and reads the PR only through `PR_REF`, so nothing from the PR executes in either event; the comment at the top of the workflow saying the checkout stays on the base is corrected to say what is true under each trigger. The trigger test in `tests/test.sh` currently greps the YAML for the trigger names; it is replaced by one that runs the workflow's shell step against a v0.0.5-shaped base (old scripts present, old trigger) and against a bare adoption base (no `.t-workflow` at all), so the transition is covered by the suite.

## Done when
- `.github/workflows/t-workflow.yml` lists both `pull_request_target` and `pull_request`, the latter with `paths: ['.github/workflows/t-workflow.yml']`, on one job named `t-workflow`; the job's steps are otherwise unchanged.
- The header comment states that under `pull_request_target` the checkout is the base and under `pull_request` it is the merge commit, and that in both cases the gate scripts come from the base by ref and the PR is only read through `PR_REF`.
- `tests/test.sh` runs the workflow's `run:` step (extracted from the YAML, not retyped) in a temporary repo with a bare origin, in three settings: a base with no `.t-workflow` (adoption: the PR's scripts run and the adoption exemption passes), a base carrying v0.0.5's `.t-workflow/scripts` and the old workflow (update: the base's scripts run against the PR), and a base carrying the new scripts (steady state: the base's scripts run). Each asserts which copy ran and the exit code.
- `tests/test.sh` asserts the `paths` filter is present on the `pull_request` trigger and absent from `pull_request_target`.
- `tests/test.sh` passes.
- `.t-workflow/AGENTS.md` needs no change unless its CI paragraph states something the two triggers make false; if it does, the smallest wording fix.

## Explicitly not
- Any change to `ci.sh`, `lib.sh`, or the config parser from #13.
- Removing the required check at install time or re-adding it after merge; the installer stays as it is.
- The task issue form's required fields, the length of the CI paragraph in `.t-workflow/AGENTS.md`, and applying the `wip/*-integration` protection rule in update mode. Each is a separate decision.

## Decisions made along the way
- The `pull_request` trigger is filtered with `paths` to the workflow file, not gated with an `if:` on the job: a job skipped by `if:` still reports a run, and under GitHub's every-run-must-pass rule a skipped run is harmless, but a path filter means no run exists at all on an ordinary PR, so nothing about the steady state changes.
- The concurrency group now carries the event name. With the old key the two runs on a PR that touches the workflow file shared one group with cancel-in-progress, so the later one would cancel the earlier, and a cancelled run counts as failed: every future `/t-update` would have been blocked. Found while planning, not by a test; the test now asserts the key.
- `rerun-ci.sh` re-runs every red completed run at the head instead of the first listed, for the same two-run case. Runs that are green, skipped, or in progress are reported as before; a failed re-run of any run exits 1.
- The test extracts the workflow's `run:` block from the YAML with awk and executes it in a fresh clone of a bare origin, with `refs/pull/1/head` set the way GitHub sets it. The three base shapes use stub `ci.sh` files that print which copy ran, except adoption, which brings the real scripts and asserts the exemption. A v0.0.5-shaped base is represented by a stub and the old trigger, not by the tag, because CI checks out without tags.
- `.t-workflow/AGENTS.md` gained one sentence, because "never its own copy" was no longer exactly true for a PR that changes the workflow file; the guarantee stated around it is unchanged.

## Deviations / notes
- Re-planned before the branch was created: `.t-workflow/scripts/rerun-ci.sh` was added to Allowed paths once reading it showed it takes the first run `gh run list` returns, which on a two-run PR leaves the other red. The original plan had said to read it and decide.
- GitHub's every-run-must-pass rule for a required check name is the load-bearing external fact and cannot be tested offline. Verified on 2026-09-11 in a throwaway repository under the maintainer's account: one job named `t-workflow` under both triggers, the check required with admin enforcement on, four PRs (honest red then forged green, forged green then honest red, both green, honest green then late red). The three mixed cases reported `mergeStateStatus: BLOCKED` and `gh pr merge` refused with "the base branch policy prohibits the merge"; only the all-green control merged.
- This PR is itself the first PR that touches the workflow file after #22, so it is judged only by the base's `pull_request_target` copy (main's file has no `pull_request` trigger yet). The first PR to touch the file after this one merges is where both runs appear.
