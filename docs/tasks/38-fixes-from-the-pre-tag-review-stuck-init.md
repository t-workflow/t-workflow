# 38 — Fixes from the pre-tag review: stuck initiatives after update, silent config lines, dead issue form, false README claim, skill wording
Issue: #38

## Asked
A cold review of every change between v0.0.5 and main, made before tagging, found nine things. None breaks a steady-state consumer, but two can stick one, one silently weakens a gate, and the rest are false or misleading statements in shipped files. They are fixed together, in one PR, so the next tag carries none of them.

1. **A partly shipped initiative sticks after an update.** Under v0.0.5 an initiative's children merged to the trunk one at a time. After the update, the next child's `/t-work` creates `wip/<parent>-integration` from a trunk that already holds the earlier child's record, and `gate.sh ship <parent>` (line 165) and `ci.sh`'s children loop demand every completed child's record be in the parent PR's diff. The earlier child's is not, so the parent blocks with "it never merged into" and nothing names a way out. Both accept a completed child whose record already exists at `origin/<trunk>:docs/tasks/<child>-*.md`, and say so in their output.
2. **Parent and child are decided by different signals.** `gate.sh` reads "child" from the issue's parent field and "parent" from the `initiative` label, so a sub-issue filed under an unlabelled parent lands on an integration branch that `ci.sh` and the ship gate never treat as a parent's. The work gate for a child blocks when the parent lacks the label and names `issue.sh ensure-label initiative` plus `gh issue edit <parent> --add-label initiative`.
3. **An ignored config line is silent.** `lib.sh`'s `load_config` accepts only `key="value"` lines with no inner quote. A consumer whose `.t-workflow/config` was hand-written with single quotes, an escaped quote, or a `$VAR` now gets an empty `check`, and the agent reports "no check configured" and skips check 1. `load_config` prints one line to stderr per line it ignores that looks like an assignment (`config: line N ignored: <text>`), and the header comment in `.t-workflow/config` and in the copy `install.sh` writes (line 378) says the file is parsed, not executed: `key="value"` only, no quotes inside the value, no variables.
4. **The README promises updaters a rule they do not get.** README lines 20 to 22 say a second protection rule covers `wip/*-integration`, but `install.sh` skips `protect.sh` in update mode, so a v0.0.5 consumer's integration branches are unprotected. Update mode runs `protect.sh` too, unless `--no-protect`; `protect.sh` is already idempotent, merging into existing rules.
5. **The task issue form is dead weight and a collision hazard.** GitHub issue forms emit every field as a `###` heading; `section()` in `lib.sh` matches `##` exactly, so `record.sh create` and `gate.sh work` have never read a form-filed issue. Adopt mode now refuses an install when a consumer already has `.github/ISSUE_TEMPLATE/task.yml`, and update mode overwrites a consumer-authored file of that name. The form is dropped: removed from `OWNED` and from the tree, and the updater deletes a consumer's copy only when it is byte-identical to the one an earlier release wrote (that is, ours), never a consumer's own.
6. **Cancelling a child already merged into the integration branch hits an error.** `t-cancel/SKILL.md` step 4 says close the PR if one exists; `gh pr close` on a merged PR errors, and the agent has to read past it to reach the revert in step 5. Step 4 says: a merged PR is left alone, the revert in step 5 is its undoing.
7. **Two skill sentences describe one CI run.** `t-ship/SKILL.md` step 2 and `t-review/SKILL.md` step 6 say `rerun-ci.sh` re-runs "it"; a PR that touches the workflow file has two runs and the script re-runs every red one. Both say "the red runs".
8. **`rerun-ci.sh` with a flag-shaped argument re-runs across the repository.** `gh pr view --help` exits 0 without JSON, `head` is empty, and `gh run list --commit ""` lists every recent run. One guard: an empty head is an error.
9. **The no-dates rule is wider than it means.** `CLAUDE.md` says a version, date, or release name never appears in the tree. Records #13, #26, #30 and #32 carry dates in prose ("verified on 2026-09-10", GitHub's change "as of 2026-07-16"), and those are facts about the outside world that the git log does not hold, so they stay. The rule is narrowed to what it was for: a version, date, or release name never appears in a shipped file (the `OWNED` list in `install.sh`), and nothing is written that a tag or the git log already says. Records and `docs/decisions.md` keep their dates.

Separately, and not a file change: the `tests (ubuntu-latest)`, `tests (macos-latest)` and `shellcheck` jobs are not required checks on this repository's `main`, so a red suite is held back only by the ship skill. `.t-workflow/scripts/protect.sh --add "tests (ubuntu-latest)" --add "tests (macos-latest)" --add shellcheck` makes them required; run it as part of this task and note the output in the record.

## Done when
- `tests/test.sh` has a case for each of 1, 2, 3, 5 and 8: a parent whose completed child's record is already on the trunk ships; a child of an unlabelled parent is blocked at the work gate with the label command named; a config line with single quotes or a `$VAR` produces an `ignored` line on stderr and the documented empty value; an update over a consumer whose `task.yml` is ours deletes it and over one whose `task.yml` differs leaves it; `rerun-ci.sh` with an empty head exits 2 and re-runs nothing.
- `install.sh` in update mode calls `protect.sh` unless `--no-protect`, and its plan output says so; README lines 20 to 22 are true for adoption and update alike.
- `.github/ISSUE_TEMPLATE/task.yml` is gone from the tree and from `OWNED`.
- `CLAUDE.md`'s rule reads "never appears in a shipped file" and names `OWNED`; `grep -rn '20[0-9][0-9]-[0-9][0-9]-[0-9][0-9]' $(sed -n '/^OWNED="/,/^"/p' install.sh | grep '^\.' )` matches nothing; the four records are unchanged.
- The three jobs are required checks on `main` (`gh api repos/t-workflow/t-workflow/branches/main/protection --jq .required_status_checks.contexts`).
- `tests/test.sh` passes.

## Explicitly not
- Making `section()` read `###` headings so the form could work. The form goes instead.
- Retargeting a child PR that was open against the trunk at update time; the ship gate's message already says its base is wrong, and `gh pr edit <pr> --base wip/<parent>-integration` is the human's one command.
- Changing what the config parser accepts. Double-quoted values only stays; it is warned about, not widened.

## Decisions made along the way
- A `$` inside a double-quoted config value was accepted before, as literal text, never expanded. The issue's done-when asks for a `$VAR` line to be ignored and said, and a literal `$HOME` is never what an author meant, so the parser now refuses a `$` in the value the way it refuses an inner quote. That is the one narrowing of what the parser accepts, and it is said on stderr rather than read as empty in silence.
- The retired form is recognised by git blob id, not by a copy of its bytes: `RETIRED` in `install.sh` carries the two ids this repository ever shipped (the tagged one and the one on the trunk after #34), and the test writes the tagged bytes and asserts their id before relying on them.
- The work gate checks the parent's label before creating the integration branch, so an unlabelled parent's child never gets a branch that CI would judge as a task's.
- The parent gate and CI accept a trunk-resident record only at the exact `docs/tasks/<child>-*.md` path on the trunk; the record itself is not re-validated there, since it passed its own gate when that child shipped.

## Deviations / notes
- `CLAUDE.md` is a symlink to `AGENTS.md` in this repository, so the rule change lands in `AGENTS.md`; the plan was amended to say so before the edit, and nothing else in the plan changed.
- The required-checks change was not made. `.t-workflow/scripts/protect.sh --add "tests (ubuntu-latest)" --add "tests (macos-latest)" --add shellcheck` is a live write to this repository's `main` protection, and the agent session's permission layer refused to run it. The command is unchanged and is the one hand step left; the record is to be updated with its output once it has run.
- `shellcheck` is not installed on the working machine; its only run is the `shellcheck` job in CI.
- `tests/test.sh`'s config-values case now silences stderr, since the lines it feeds the parser are exactly the ones the parser now reports; the new case next to it asserts the reports.
