# 10 — install.sh must recognise the old t-workflow by its shape, not only by its manifest
Issue: #10

## Asked
`install.sh` recognises the old template-based t-workflow only by `.template-manifest.json`, but a repository generated by the old bootstrap never got one (the manifest arrived with the old `/t-update`, which not every consumer ran). On such a repository, `t-preview/t-preview` among them, the installer picks adopt mode, copies the new files over the old, and leaves the old constitution, ADRs, adapter and architecture docs, migrations, CI workflows, and `t-config` skill in place, with the pointer line prepended to a 14 KB `AGENTS.md` that contradicts the new contract. The old workflows then fail on every PR because the scripts they call are gone. The installer must recognise the old t-workflow by its shape and remove what the old template shipped, with or without a manifest.

## Done when
- Replace mode triggers when `.template-manifest.json` exists **or** when `CONSTITUTION.md` and `.t-workflow/scripts/protected-paths.sh` both exist.
- Without a manifest, the removal set is a built-in list of what the old template shipped, by name: `.claude/skills/t-*`, `.t-workflow/scripts/*.sh`, `docs/adr/0[0-9][0-9]-*.md`, the old template's `docs/architecture/` and `docs/adapters/` documents by filename, `docs/workflow.md`, `CONSTITUTION.md`, `AGENTS.md` (slots harvested first), `.github/workflows/ci.yml` and `review-gate.yml` (slots harvested first), `.github/ISSUE_TEMPLATE/{task,initiative,config}.yml`, `docs/tasks/README.md`, `migrations/`. A consumer's own files under those directories are untouched.
- With a manifest, behaviour is unchanged, except that the same by-name list is also applied, so a consumer file the manifest missed (a `t-config` left behind, a `migrations/` copy) does not survive.
- `.t-workflow/required-checks.local`, when present, is carried into `.t-workflow/REPLACED.md` rather than silently deleted.
- `tests/test.sh` gains a bootstrap-shaped fixture (old layout, placeholders in every slot, no manifest) and asserts the result matches the manifest-shaped fixture's: old files gone, consumer files kept, config and `AGENTS.md` built the same way.
- The installer prints which mode it chose and why (manifest, or shape) before touching anything.

## Explicitly not
- Closing a consumer's open old-template PRs or deleting its stale branches; the installer reports them, a human decides.

## Decisions made along the way
- The by-name removal list is applied with and without a manifest, so a file the manifest missed (a `t-config` left behind, a `migrations/` copy) never survives (agent, 2026-09-09).
- The leftovers report skips empty slots and the old workflows' default `timeout-minutes: 10`, and is not written at all when nothing real was found (agent, 2026-09-09).

## Deviations / notes
- Found while building the fixture: the old check slot's placeholder text carries example commands in backticks (`npm test`, …), and the harvester took the first as the project's check command. It now recognises the placeholder. t-preview would have been given `check="npm test"` with no stack.
- Verified against a scratch copy of t-preview's real tree: 75 files to 33, every old file removed, consumer files kept, config at defaults, no leftovers report.
